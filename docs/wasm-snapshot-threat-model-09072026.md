# wasm/native snapshot — plaintext at rest, and why that's the scoped answer

**Date:** 2026-09-07
**Status:** Record only. No code. Closes the narrowed remainder of the void P-1 (`remediation-plan-persistence-encoding-09072026.md` §8) and phase-5 §8.

---

## What this is

`rust/src/state_snapshot.rs` is the persistence surface for the `wasm32-unknown-emscripten` staticlib embedding (`openssl.wasm`, the pkcs11-provider build). The Rust engine keeps all token state in memory; `openssl.wasm` is built with `-sEXIT_RUNTIME=1`, so every `callMain()` tears the runtime down and `C_Finalize` zeroizes the object store. Without a snapshot taken before that wipe, a token key generated by one CLI invocation would not exist for the next — the module doc states this is the same failure mode the C++ engine avoids with its file-backed token directory.

Format: versioned little-endian binary, magic `SHR3SNP2` (bumped from `SHR3SNP1` on 2026-08-13 when the stateful HBS attribute ids moved into engine-private space — an old-format snapshot is refused outright, never reinterpreted). Scope: token/slot metadata and PIN hashes, `CKA_TOKEN=TRUE` objects, and the handle/unique-id counters — session objects and login state do not survive.

**On native builds**, the same code path is reachable through an opt-in environment variable, `SOFTHSMRUST_STATE_FILE` (`ffi.rs:328`, `:382`) — off by default, byte-identical to in-memory-only behaviour when unset.

## The comparison this note replaces

An earlier finding (this programme, 2026-09-07) compared this blob against the two **native, PIN-derived-key, encrypted-at-rest** stores and reported it as the same kind of gap. It is not:

| | Protection | Reachability |
|---|---|---|
| C++ `SecureDataManager` | Encrypted, token-key-wrapped | Native only |
| Rust `crate::store` | Encrypted, PIN-wrapped master key, AES-256-GCM, PBKDF2-HMAC-SHA256 @ 210,000 iterations | Native only |
| **This snapshot** | **Plaintext** | wasm (always) · native (opt-in env var only) |

The two native stores are each engine's real production persistence and were confirmed encrypted at rest during this programme (`remediation-plan-persistence-encoding-09072026.md` §8). This snapshot is a different artefact serving a different purpose, and conflating the two produced a wrong finding and a half-built duplicate key hierarchy before it was caught.

## Why plaintext is the right scope, not a gap

1. **The browser case has no filesystem to protect against.** The blob lives in the host's own memory/storage (however the embedding page chooses to persist it) — the host is *already* the party holding the bytes. Encrypting it under a key the host also holds protects against nothing; the host is the trust boundary, not a third party.
2. **On native, the mechanism is opt-in and narrow.** `SOFTHSMRUST_STATE_FILE` must be explicitly set; unset, behaviour is unchanged (nothing written, nothing read). Its one mitigation already lands where it can: the file is written with mode `0600` on Unix (`ffi.rs:386-389`) — as tight as a bare filesystem permission gets without a key to derive from.
3. **There is no PIN-equivalent secret available to derive a key from in either case.** The native stores' encryption is PIN-wrapped; this snapshot's native path is a CLI/test fixture convenience with no login step of its own to draw a key from, and the wasm path has no analogous secret at all — only the host, which already has the blob.

## What would change the answer

If a future embedding gives the browser-side host a real secret unavailable to whatever it's defending against (a per-origin key, a hardware-backed wrap in a specific browser API), that changes the trust boundary and this note should be revisited. Absent that, encrypting this blob would add a key management problem without a party to keep the key from.

## Disposition

**No code.** This is the deliberate, now-recorded scope boundary: the wasm/native snapshot is plaintext by design, for a different threat model than the two native stores, so the next reader does not rediscover it as a finding.
