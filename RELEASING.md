# Releasing

A version bump is the moment compliance claims get published (CHANGELOG,
README, the two conformance reports) and read by people outside this repo.
The core local gate (`bash scripts/local-gate.sh`) is enough for an ordinary
PR; a release needs the full evidence set behind it.

## Checklist

1. **Run the full gate**, including the opt-in suites:

   ```bash
   bash scripts/local-gate.sh --all
   ```

   This runs everything the core gate does, plus:
   - `--cpp` — the C++ `ctest` suite, incl. `p11_v32_compliance_test`
   - `--acvp-wasm` — the 20-suite cross-engine ACVP wasm harness
   - `--rust-p11` — the Rust engine's PKCS#11 v3.2 conformance matrix
   - `--tls-interop` — the §3.3.3 hybrid-TLS-vs-OpenSSL-3.6 proof (needs an
     OpenSSL ≥ 3.6 build reachable via `OPENSSL_BIN`/`OPENSSL_LIB_DIR` — see
     the comment above this step in `local-gate.sh` for how to get one into
     the Rust container)

   A run missing `--tls-interop` because no OpenSSL ≥ 3.6 oracle was
   available is a real, note-worthy gap, not a silent skip — say so in the
   release notes rather than letting the §3.3.3 claim imply it ran.

2. **Regenerate and commit current evidence** in the release commit itself,
   not a follow-up:
   - `cpp_compliance_report.{json,md}` — regenerate via the C++ suite,
     `--engine-commit` set to the release commit
   - `rust/RUST_P11_V32_CONFORMANCE_REPORT.md` — regenerate via
     `scripts/local-gate.sh --rust-p11` (writes the report; see
     `rust/test_p11_conformance.js`)
   - `kmip/conformance/REPLAY_REPORT.{md,json}` — regenerated by the gate's
     OASIS replay step; commit if `check_report_fresh.py` shows a diff
   - `kmip/docs/CONFORMANCE_REPORT.md` — update its "Current as of" header
     and any table whose underlying behavior changed this release

3. **Reconcile every published pass count** — README.md, CHANGELOG.md, and
   the reports above must agree. A reviewer who greps the release diff for
   the new pass/fail numbers should find exactly one figure per suite, not
   three.

4. **Update `.gate-ok-<sha>` implicitly** — step 1 writes it for the release
   commit; the pre-push hook (`scripts/git-hooks/pre-push`, installed via
   `scripts/install-hooks.sh`) will not let the release push happen without
   it.

5. **Tag and update CHANGELOG.md** — move `[Unreleased]` entries under the
   new version heading with the release date.

## Why this is a separate document from CONTRIBUTING.md

CONTRIBUTING.md's local-gate step is what every PR needs. This checklist is
stricter and slower by design — it exists because two prior releases
(0.23.0, 0.24.0) shipped compliance claims (a differential-harness figure,
a hub-side cross-check, the Rust PKCS#11 matrix) without a fresh, in-repo,
commit-stamped run backing them at the moment of release.
